# D4 好友音乐杯

4/8 人固定种子单淘汰，按场次依次复用真实双人引擎。默认 10 对 10（选 12/BAN 2），可选 15 对 15（选 18/BAN 3）。赛事组织器只管理对阵和晋级，分数及胜负来自绑定的单场会话。界面沿用独立音乐派对设计，不复制 Karuta UI。

## 操作

1. 大厅切换好友淘汰赛，4 或 8 位好友填写/跳过画像后全员准备。
2. 房主创建对应人数的赛事。名单、规则和画像版本立即固定。
3. 房主安排待开始的场次；每场第一位选手负责共享音箱和最终开局。另一位确认歌牌，旁观者不能抢牌、报告播放或中断。
4. 双方选歌/BAN，按最终题组重评。公平告警必须明确确认；短库不可绕过。
5. 先清空手牌者晋级。房主即使已淘汰仍可安排后续场次。完成决赛后所有成员看到同一冠军。
6. 平局等待双方加赛；断线/播放失败只中断本场，不自动弃权。本人弃权或组织者处理需要确认及原因，记录操作者、选手、场次和时间。

## 一致性与素材

每场结果绑定 match、完整 session、双方、rulesVersion 与 resultVersion；重复结果幂等，冲突及跨会话结果拒绝。准备请求另绑定 matchId/attempt，旧场迟到请求不会进入新场。服务端没有客户端提交分数或晋级结果接口。

正常完成局的逐题反馈写回个人画像，但本届赛事始终使用赛前画像，每场只投影双方。SONG_STARTED 即记录全赛事曝光，中断也保留；默认排除已播歌。可用前奏不足时暂停安排，组织者明确允许跨场重复后才重新评估。

管理员可更新服务器配置的素材审计与核验清单，在两场之间由房主点击“刷新已核验题库”。服务器重新校验文件哈希并生成去元数据片段，只向该房间补充新核验内容，保留所有已发布录音/卡牌及音频映射。加载失败不修改房间；加载期间版本变化拒绝应用。题库更新后旧选歌/准备作废，双方重新确认。浏览器不能指定文件路径、上传核验结果或自行激活素材。该入口更新当前房间；新房间默认仍使用进程启动时题库，重启服务后统一采用新清单。

赛事活动期间不能修改参赛画像与模式。晚加入者保持旁观至赛事结束。比赛中对阵默认折叠，减少手机页面滚动。

## 验证边界

四个独立 Chrome 完成真实两场半决赛与决赛，四端冠军一致。分数依次为 6/0、10/0、8/0，累计曝光 37 首、剩余 68 首；冻结画像均为版本 1，个人画像随反馈更新。自动点击依据当前音频哈希匹配可见卡牌，未读未来题序、未改分或加速时钟。用户提出静音要求后，四个测试 Chrome 均以 --mute-audio 重启，后续验证全程静音；不修改其他应用音量。

八人七场真实引擎、平局、断线、弃权、重复/冲突结果、曝光排除、冻结画像、短库、素材增补与请求权限由单元和 HTTP 测试覆盖。原浏览器长赛程早于最终补库入口，最新构建另验补库/UI；两者范围在 [结构化记录](evidence/d4-browser-validation.json) 中区分。

房间为内存状态，服务重启不会恢复。现场真人听辨、QQ WebView 真机和 QQ 官方授权/API 尚未验收；这些不能由自动浏览器结论替代。完整演示步骤见 [演示手册](demo-walkthrough.md)。
