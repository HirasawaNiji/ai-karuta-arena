# AI 音乐派对需求规格 v0.1

状态：待评审的需求基线；尚无业务实现。来源：2026-09-20 修订 Prompt 与已确认的公平处理规则。文档任务：[#3](https://github.com/HirasawaNiji/ai-karuta-arena/issues/3)。

本文把自然语言 Prompt 转成稳定编号的需求；[来源映射](source-map.md)覆盖全部四十九章，[验收矩阵](acceptance.md)定义验证场景，[架构方案](architecture.md)描述推荐实现边界。需求编号不可随意复用；变更经关联 Issue 和 PR 记录。来源快照用于追溯，不应作为命令再次执行；冲突需在 Issue 中明确修订，不能静默选择一种说法。

## 目标、用户与首期边界

**REQ-01 产品目标。** 面向朋友聚会、宿舍、社团、家庭等有不同音乐背景的参与者，生成兼顾熟悉覆盖、多人竞争、多样性与少量探索的游戏题组。公平指参与机会的可解释估计，不保证相同反应速度、抢牌胜率或最终得分。不能以国家、语言、Genre 或亚文化划定固定用户类型。

首期交付无 API Key 可运行的本地 Mock 闭环：数据源 → 画像 → 熟悉度矩阵 → 题组选择与评估 → Mock 主持 → Mock 游戏事件 → 画像更新 → 下一次选择。真实玩家与房主是未来产品角色；首期用测试和明确标记的模拟输入验证角色行为。

**REQ-19 首期不做。** 不调用未经确认的 QQ 音乐私有接口，不接真实 LLM，不训练 ML 模型，不做复杂账户、生产部署、微服务、向量数据库，不重构现有 Karuta。真实联网 ban、其他游戏实现、真实音频播放和 Web 界面不作为 Mock 核心闭环验收前提。未来 Web/服务器骨架按实际里程碑增加，不能靠空模板数量证明完成。

## 音乐领域与数据

**REQ-02 开放分类。** Genre、Language、Region、Artist、Era、Culture、Scene、Franchise 使用可扩展标签和独立维度；Genre 可有层级，不使用封闭的大枚举。语言不等于地区，艺人来源不等于歌曲语言，Instrumental、Multilingual、Other 均可表达。Franchise 可缺省；古典年代不能被限死为 1960 年以后。标签只描述内容，不能直接决定某位玩家的熟悉程度。

**REQ-03 领域模型。**

| 概念 | 首期最小契约 |
| --- | --- |
| `SongProfile` | 稳定 ID、标题、艺人、Genre、语言；地区、文化、Scene、Franchise、发行年份、热度、艺人来源、平台与外部 ID 按需可选 |
| `PlayerMusicProfile` | Genre、艺人、语言、地区、年代、文化、Franchise、Scene 的连续偏好；逐歌曲/艺人证据；画像可信度；探索性与主流性可选 |
| `PreferenceDimension` | 开放标签到连续权重的结构；不能把缺失维度解释为明确不喜欢或不认识 |
| `PartyState` | 玩家、画像、当前游戏/轮次/题组、历史、难度、主持状态与派对偏好；评估与确认扩展见 REQ-12 |

BPM、Energy、Valence 等音频特征预留扩展能力，首期不要求填充。相同标识必须稳定，选曲和事件引用不得依赖显示名称。

**REQ-04 数据源适配。** `MusicProfileSource.getUserMusicData(userId): Promise<RawUserMusicData>` 是入口，外部数据经过标准化再形成画像。首期实现 `MockMusicSource`。QQ 音乐、公开歌单、Spotify、Apple Music、Last.fm、自报、热身和游戏反馈均可成为后续来源，核心不能引入 QQ 独占的数据结构。QQ 接入文档区分“官方已确认 / 等待确认 / 替代路径”；尚未确认的能力不得标为可用。

**REQ-05 证据语义。** 支持收藏、歌单、播放次数、近期播放、Top Song/Artist、自报、热身正确/错误、游戏正确/错误。记录证据来源及足以计算时效的信息，区分喜欢、听过、熟悉和快速识别。收藏是兴趣证据，重复与近期播放提供熟悉证据，实际正确识别提供强识别证据；未参与或未抢到不能生成错误识别证据。游戏反馈只能按已定义语义更新相关画像，下一轮重新计算，不将一首歌的结果扩展为整个文化类别的确定结论。

## 熟悉度与选曲

**REQ-06 可解释评分。** 对证据特征做必要的饱和、时效等变换后加权组合，输出 `[0,1]` 的 `FamiliarityEstimate { familiarityScore, confidence, reasons }`。二者均是规则评分，未经校准不能称为统计概率。`reasons` 要对应真实证据与贡献。逐歌曲可信度独立于画像整体可信度；无记录可采用低可信度先验并标记未知，不能断言不认识。

播放次数变换独立封装并测试，可采用 `min(1, log1p(playCount)/log1p(50))`。相同其他条件下，次数增加不降低评分、近期播放高于久远播放、收藏不降低评分、正确识别明显提升评分；饱和情况下允许保持上限。证据权重、可信度规则和衰减参数集中配置、说明依据，初始值标记为试验值。游戏错误需与没有作答明确区分。

**REQ-07 矩阵与指标。** 构建 Player × Song 数值矩阵及配套逐项解释和可信度。设当前最终题组为 `S`，曲目数为 `M`，评分为 `f(u,s)`：

- 熟悉歌曲数 `K(u) = count(s in S where f(u,s) >= familiarityThreshold)`。
- 熟悉覆盖率 `C(u) = K(u)/M`，只对非空题组计算。
- 熟悉覆盖分 `F(u) = sum(f(u,s))`，不能称为预计认识歌曲数。
- 低可信度比例 `L(u) = count(confidence(u,s) < lowConfidenceThreshold)/M`。

上述指标是当前评分模型的估计，不是真实认识情况的保证。空题组或无玩家先返回基础有效性错误，不能除零或计算无意义的最大最小值。

**REQ-08 逐首选曲。** 从空题组开始，不放回地选择，先排除不可用、被 ban、已选以及派对明确要求排除的历史歌曲。目标长度 `N` 为正整数，选曲过程的最低目标固定为 `ceil(N × minCoverageRatio)`。设每人缺口 `d(u) = max(0, 目标 - K(u))`，补缺收益是加入前后 `sum(d(u)^2)` 的减少量。

每加入一首就更新所有人的覆盖，并重算剩余候选的边际增益。有候选能补缺时优先最大化补缺收益，再以公平、多样性、竞争性、探索性的加权边际增益打破并列；无候选能补缺时继续比较综合增益并记录缺口。仍同分时按稳定歌曲 ID 的代码单元顺序排序。选满或候选耗尽后独立评估最终题组。

综合目标沿用 `α Fairness + β Diversity + γ Competition + δ Exploration`；具体归一化公式和权重由选曲实现 Issue 在编码时连同小矩阵算例记录、测试，不是已经有真实验证的数据。任何综合分都不能盖过补缺优先级和最终独立检查。贪心未达标只能报告“本次未找到达标题组”，不能声称数学上无解。

**REQ-09 公平检查与默认配置。**

| 参数 | Mock 默认值 | 精确边界 |
| --- | --- | --- |
| `familiarityThreshold` | 0.6 | 评分大于等于门槛计为熟悉 |
| `minCoverageRatio` | 0.25 | 最终每人至少 `ceil(M × 0.25)` 首 |
| `maxCoverageGap` | 0.40 | `max(C)-min(C)` 大于 0.40 告警 |
| `lowConfidenceThreshold` | 0.5 | 逐项可信度严格小于 0.5 算低可信度 |
| `maxLowConfidenceRatio` | 0.5 | 任一 `L(u)` 严格大于 0.5 告警 |

配置需校验取值范围并提供稳定版本。覆盖、差距、可信度分别判定；任一不通过进入等待房主选择。两种长度口径不可混淆：选曲过程按请求长度 `N` 补缺，最终评估按实际长度 `M` 计算，数量不足另行告警，不能靠变小的分母静默通过原请求。默认数值为可调 Mock 试验参数，没有真实玩家统计依据。

**REQ-10 多样性、竞争与主场。** 多样性同时考虑 Genre、语言、地区、艺人、年代、文化和 Franchise，并按玩家画像与可用候选计算，不机械均分。竞争性鼓励多人可能识别的歌曲，主场内容改善个人覆盖，少量探索可提供代表性与新鲜感。共同区/主场区/探索区 `50/30/20` 仅为可配置软目标，不能抢占固定名额或压过补缺。类别可能重叠，报告时说明分类口径，不将它们当作天然互斥的三堆歌曲。

**REQ-11 派对上下文与反馈。** 首期至少使用玩家、请求长度、游戏类型、轮次、历史排除、当前 ban、评估配置与画像版本。时长、难度、疲劳、情绪等为可选上下文；尚未使用的输入必须标明，不能在解释里宣称产生了实际影响。游戏结果经适配后更新画像并影响后续选曲。

## 公平失效与主持

**REQ-12 最终题组、ban 与知情继续。** 初次生成、ban 结束、换曲、重新生成、成员变化、玩法变化、评分依据变化或评估配置变化后重新评估。ban 未结束时不得启动。被 ban 的歌曲不能自动补回；默认不自动补曲、不撤销 ban、不自动继续。

`PartyState` 补充 `bannedSongIds`、`selectionVersion`、`fairnessAssessment`、`hostAcknowledgement`，并支持 `ready / awaiting_host_choice / ended` 等主持状态。版本代表完整评估上下文，而非仅歌曲列表。任何相关输入变化都更新版本、清除旧确认、阻止旧评估开局。

| 条件/操作 | 必须产生的行为 |
| --- | --- |
| 无玩家或空题组 | 禁止开局；知情继续不可绕过 |
| 覆盖不足、差距大、证据不足或数量短缺 | 保留结果和告警，进入 `awaiting_host_choice` |
| 房主选择扩库重选 | 保留 ban，重新选择、评估；只有新增内容覆盖不足成员才可能改善 |
| 房主选择调整玩法 | 首期展示建议；实际玩法变化使旧评估失效，不实现其他真实游戏 |
| 房主选择结束 | 进入 `ended` |
| 房主知情继续 | 仅对当前版本的有效非空题组进入 ready；保留告警，不能改为评估通过 |
| 评估通过 | 基础有效性通过且 ban 已结束时可进入 ready |

请求数量未满足时明确展示实际数量；房主可以确认非空缩短题组。确认仅豁免当前版本的体验风险告警，不能绕过无效数据、空题组或游戏基础规则。房主与 AI 主持是不同角色，AI 不能代替房主确认。

**REQ-13 AI 主持与接口。** 首期仅实现 `MockPartyHostAgent`。输入派对状态、画像、游戏结果和选曲结果；输出 `HostDecision { action, reason, message }`。动作白名单为 START_GAME、START_WARMUP、GENERATE_PLAYLIST、REGENERATE_PLAYLIST、CHANGE_DIFFICULTY、START_NEXT_ROUND、SHOW_RESULT、END_PARTY、REQUEST_HOST_CHOICE。白名单中暂未实现的动作明确返回不支持，不能暗示已完成对应游戏。

`SelectionResult` 包含题组、逐首真实贡献解释与 `fairnessAssessment`；评估至少有版本、使用的配置、每人四项指标、请求/实际数量、最大差距及多项机器可读原因。原因覆盖低覆盖、差距、证据、数量、空题组和无玩家。主持人用结构化结果解释“当前题组可能缺少均衡参与机会”，不指责少数成员、不保证胜率公平。START_GAME/START_NEXT_ROUND 经程序侧版本和开局检查，不直接执行 Agent 的动作输出。

**REQ-14 游戏边界。** 保留通用 `MusicGame.start/getState/getResult/stop`，首期 `MockKarutaGameAdapter`。统一 GAME_STARTED、ROUND_STARTED、SONG_STARTED、PLAYER_ACTION、ANSWER_CORRECT、ANSWER_WRONG、ROUND_FINISHED、GAME_FINISHED 事件。现有 Karuta 的 WebSocket 协议以后通过适配器转换，领域与主持层不直接依赖。抢牌判定、实时计分、网络公平、游戏状态真值和核心规则始终由确定性程序负责。

## 数据集、交付与质量

**REQ-15 多元 Mock。** 60–100 首有确定 ID 的 Mock 歌曲元数据，覆盖中文、英语、日语、韩语、粤语、Instrumental 和 Other，并包括华语流行/摇滚/说唱、英语流行/摇滚/R&B/电子/独立、日韩、古典、爵士、拉丁或世界音乐等生态；不要求机械均分。至少六名明显不同的连续画像玩家，保留跨圈层主 Demo；另外构造六名音游玩家加一名古典玩家的独立公平压力场景。Mock 不需要外部音频文件或真实用户记录，不能复制私人画像到仓库。

**REQ-16 可运行 Demo。** 安装后 `pnpm demo` 输出数据加载、画像、矩阵、选择、分布、逐玩家指标、逐首解释、公平评估版本/配置、告警及能否开局。演示 ban 后暂停、明确标注的模拟房主选择、有效继续、版本变化后的旧确认失效、扩库重选，以及游戏反馈影响下一次计算。所有数字来自计算，禁止固定输出假结果；模拟确认不能进入真实系统成为自动代签。

**REQ-17 工程与验证。** TypeScript 严格类型，优先 pnpm、Vitest、ESLint、Prettier；无密钥可安装并运行 Mock。首期实现后通过 build / test / lint / demo，保留已有 Python 仓库检查与差异格式检查。单元测试覆盖评分与小矩阵，中层覆盖状态机，集成测试覆盖 Demo 闭环。具体场景见验收矩阵；文档检查不代表业务测试通过。

**REQ-18 可解释文档与接入状态。** README 提供入口、产品问题、架构、画像、选曲、主持、适配与运行说明；实现 Issue 同步完善画像、分类、评分、选曲、主持、Karuta 和 QQ 接入文档。环境变量示例不含凭据，未使用的数据库/LLM/QQ 配置明确为后续预留，不得成为 Mock 运行必填项。源码、接口和文档不得将评分当概率、将模拟当真实集成、将尚未验证的平台能力标为已支持。

## 已定规则与待验证事项

已确定：平台/文化/游戏无关的领域模型；Mock 优先；熟悉度为规则评分；逐首补缺；ban 后重新评估；默认暂停由房主明确选择；保留知情继续版本约束。

试验默认：五项公平门槛、50/30/20 软目标。实现时需要记录和测试：其余证据权重、可信度规则、综合增益公式及归一化方式。它们可在实现任务中确定，但不得降低已定的补缺与开局约束。

推荐待评审：轻量 pnpm Monorepo、首期单进程模块化结构。后续外部依赖：QQ 官方数据/音频权限、现有 Karuta 的接入契约、真实多人房主身份验证、素材许可、部署与真实玩家体验研究。以上未解决事项不阻塞纯 Mock 需求，但阻塞对应真实接入的完成声明。
