# 本地连接诊断

当页面首次导航、SSE 建连或 HTTP 回归出现连接超时，先区分请求是否到达服务，再处理应用状态。#38 已修复的过期心跳恢复不等于 #39 的建连问题已解决。

## 可重复探针

使用仓库指定 Node/pnpm，执行：

~~~sh
pnpm network:check --mode stable --client http --samples 50
pnpm network:check --mode fresh --client fetch --samples 2000
~~~

stable 使用同一个监听器，每次请求间隔 10 毫秒；fresh 为每个样本新建并关闭监听器。http 客户端每次新建连接；fetch 保留 Node 原生连接池行为，与项目 HTTP 测试一致。默认 stable/fetch/50，最多 2000 个样本，每次连接最多 3 秒。工具只访问自己创建的 IPv4 回环服务，不访问项目房间、其他本机服务或外网，不读取凭据或代理配置，不改变网络设置。

输出一行 JSON，包含模式、样本数、通过数、首个失败及 TCP/HTTP 对照结果。receivedRequests 表示服务端收到请求的数量，acceptedConnections 表示服务端接受连接的数量；connected/responded 分别记录客户端连接和响应事件。fetch 不暴露 TCP 接入事件，失败时 connected=null 表示未知；需结合服务端计数判断，不能把 null 当成确认未连接。输出没有地址、端口、会话、环境变量或原始系统错误消息。

- 退出码 0：本次采样全部通过，仅证明这次采样，不证明偶发问题消失。
- 退出码 1：采样出现失败，或探针未能建立/清理；后者不输出成功报告。
- 退出码 2：参数无效，不启动监听器。

首次 HTTP 失败后，只对同一监听器各做一次 TCP、HTTP 对照，然后结束。对照成功不能把原失败改成通过；探针不内置“重试至通过”。所有连接和监听器在退出前关闭。不要把这个诊断命令插入玩家流程、用它跳过回归或据此放宽超时。

## 已有证据和边界

#39 调查使用不加载项目模块的原生 Node 服务/客户端。新建监听器模式多次出现连接超时，且应用没有接收到连接或请求；对照有时立即恢复，有时原始 TCP、原始 TCP 发送 HTTP、Node HTTP 和显式直连 Agent 都继续失败。一次持续失败窗口内，独立 .NET TCP 与 curl 也超时，系统侧可观察到监听及未完成的 TCP 握手。这将该样本定位到应用 HTTP 处理前，不能归因于派对准备或心跳代码；具体系统原因尚未确定。

同一长期监听器上的 1000 次新 HTTP 连接曾全部通过。两种采样不是同一条件，不能据此推断所有浏览器/SSE 现象同因；最初 SSE 停滞的旧 trace 仍缺少服务端接入时序。PR #40 独立 CI 的浏览器 10/10、Windows/Ubuntu 核心各 521/521 也不等于本机问题消失。

后续调查应在失败当时匹配探针自己的监听器与 TCP 状态，记录请求是否到达，再比较独立客户端；保持原始失败和采样条件。只观察任务自身服务，不停止其他预览、不全局清理连接、不关闭防火墙或擅自重置网络。涉及系统变更时先提出有证据的具体方案。浏览器始终静音；原始 trace 含测试会话，仅保留本地，公开 Issue 记录脱敏结论。

该脚本提供可交接的排查入口，不是应用修复。#39 的完成状态以 Issue 最新证据为准。
