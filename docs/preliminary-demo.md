# 初赛可玩 Demo 架构补充

修订日期：2026-09-24。依据用户确认的游玩流程：先刻画 n 名玩家的音乐画像，再进行多人同场抢牌或经典 1v1，1v1 可由赛事组织器编排。初赛暂不接大模型。本文是本次 PR 的显式范围修订，未表示任何功能已经实现。

## 1. 与已有需求、Mock 里程碑的关系

原 [REQ-01–19](requirements.md) 的平台/文化无关、可解释评分、公平补缺、禁歌重评和程序判定继续有效。原 M1–M5 / AC-01–20 保留为无密钥、无真实音频依赖的核心验证，不再被称为完整初赛可玩产品。本文增加 PRE-01–08 与 PAD-01–10；真实房间与音频的交付按本文推进，不用原 REQ-19 的 Mock 范围排除它们。

遇到范围冲突：Mock 核心仍按原文验收；初赛可玩演示按本文验收。原始 Prompt 快照不修改。新实现不得把 CLI 模拟结果冒充真人抢牌，也不能为接 UI 静默删除原有公平检查。

| 能力 | 初赛默认范围 | 后续扩展 |
| --- | --- | --- |
| 用户画像 | 标签选择、熟悉歌曲选择；可选模拟平台数据 | 官方 QQ 授权与真实喜欢/歌单/次数 |
| 题库 | 人工核验的歌曲、音源片段、卡牌映射；规则选曲 | 更大的真实来源和更多片段类型 |
| 多人模式 | 同房间全部准备后，锁定题组，随机不重复出题，抢牌数量排名 | 更大人数、远程延迟补偿 |
| 1v1 | 优先复用现有歌牌引擎；单场对战 | 多种战斗规则 |
| 赛事 | 单场先跑通，再补单淘汰赛；作为初赛目标中的独立交付 | 小组单循环、分组晋级组合赛制 |
| 主持 | 程序规则和固定文案，开场/告警/结算 | 真实 LLM 暂缓，无初赛依赖 |
| 运行 | React/Vite 页面、单个 Node 服务、内存状态，受控演示网络 | 账户、数据库、正式部署 |

初赛完整目标是手动画像 + 可玩题库 + 1v1 + 多人同局 + 简单单淘汰。先交付单场可玩切片，不要求一次完成全部模式；循环赛记录在架构中但不阻塞初赛。建议首轮联调使用 2–8 人，属于待测运行配置，不是领域模型对 n 的固定限制。QQ 不可用时仍可完成完整演示；不接 LLM，也不实现 LLM 生成题库或自动标签补全。

## 2. PRE-01：画像采集与个人曲库

玩家用昵称加入派对，无需注册账户。推荐流程：选几个音乐标签 → 从已知目录搜索/选择几首熟悉歌曲 → 可选导入平台数据 → 准备。各入口可单独使用，允许跳过并保留“信息不足”；不强迫用户授权 QQ 或填写自己不熟悉的内容。

标签支持曲风、语言、年代、艺人、文化等独立维度；初赛用少量可搜索的展示标签，底层仍是开放注册表。被选标签默认 weight=0.8、confidence=0.4，未选不代表不喜欢。默认值集中在 `onboarding-v1`，不是固定用户类型。

熟悉歌曲可选“听过 / 熟悉 / 前奏就能认出”；推荐选 3–5 首，不设成不可跳过门槛。必须保存选择对象、歌曲版本、识别范围和输入时间；“前奏就能认出”是自报强证据，不是实测正确，也不能提高抢牌胜率指标。

`ManualPreferenceSource` 把标签和歌曲自报转为标准输入；`MockMusicSource` 保留用于基础演示和测试。`QQMusicOfficialSource` 只在官方字段与授权确认后实现；喜欢、歌单、次数分开记录。缺少播放次数标未知，不能用收藏次数代替，也不依赖未经确认的私有接口。

个人曲库是与玩家证据有关的 SongId 集合及其来源，并非直接等于正式出题列表。派对候选曲库取个人内容的并集，再加入房主选定的人工公共曲库。重复同录音去重；无法匹配歌曲版本、缺音源或缺卡牌的记录保留为不可用诊断，不自动造题。

## 3. PRE-02：歌曲、录音、题目、卡牌分开

| 对象 | 最小契约 | 规则 |
| --- | --- | --- |
| SongProfile | 既有歌曲 ID、名称、艺人和标签 | 是曲目描述，不隐含播放片段 |
| Recording | recordingId、songId、versionLabel、audioAssetId | 原版、翻唱、现场版分开；不跨版本声称前奏熟悉 |
| AudioAsset | assetId、受控资源路径、时长、可用状态、使用范围记录 | 授权/素材来源待核实则不可进入实际可玩库 |
| Question | questionId、songId、recordingId、startMs、durationMs、segmentKind、answerCardId | segmentKind 为 intro/chorus/other；时段必须在音源内，正确映射经人工核验 |
| Card | cardId、answerKind、展示文字、可选图片资源 | 初赛默认歌名文字卡；answerKind 可扩展，不能强制歌曲关联动漫/IP |

初赛每场每首歌只选择一个已核验题目，先支持前奏片段；不自动切片、不做音频识别或训练分类器。D0 若发现现有引擎卡牌格式不同，适配器进行显式映射；不能未核对就保证文字卡接入已可用。

题库流水线为：个人曲库 → 派对候选歌曲 → 有合法可播片段与卡牌映射的题目 → 公平选择本局题组 → 锁定题组并生成出题顺序。可玩性过滤发生在选曲前；排除原因包含素材不可用、片段越界、映射不唯一、版本不明。

公平模块先沿用一歌一个 cell 的接口，由选曲输入准备层对本局固定 question 计算该歌的识别评分，并附 `questionBySongId`；更换片段、录音、卡牌规则都改变评估版本。后续一歌多题才需要独立 Player×Question 引擎，不在初赛过度泛化。

## 4. PRE-03：识别证据扩展

原 score-v1 用于 Mock 回归保持不变。可玩演示使用显式 `score-v2-manual`，以解决只靠歌曲自报时原 0.35 权重无法达到熟悉门槛的问题，不偷偷把收藏升级成识别正确。

新增 RecognitionEvidence：保留 evidenceId/playerId/sourceId/observedAt，以及 `songId, recordingId?, questionId?, segmentKind?, recognitionLevel`。旧 self_report 数值仍兼容；新增级别保留原枚举输入，不先抹平成单一数值。

- “听过”给自报下限 0.25，“熟悉”给 0.65，“前奏就能认出”给 0.85；自报 confidence=0.6。值是可配置试验评分，不是概率。
- v2 在旧算法的 base 之后，先做 `base=max(base, applicableSelfReportFloor)`，再用原正确下限和最新错误惩罚。收藏、播放次数及各类 affinity 的权重不变。
- 普通“熟悉”可作用于同歌的歌曲级估计，但标记为 general；前奏下限只应用到相同 recording 的 intro；如未指定 recording，保留歌曲级“熟悉”0.65，不能提升任意版本前奏到 0.85。未匹配范围不使用该 0.85 下限。
- 同玩家、同来源、同范围选择采用最新值；不同范围保留。当前题目可用多个范围时先取最具体匹配（question > recording+segment > recording > song），相同具体度再取最新观测和稳定 ID。明确降低自报会替换旧自报，不能因 max 永久保留历史强标签。
- 游戏证据保存 questionId/recordingId/segmentKind。v2 的正确下限、错误惩罚及相应 confidence 仅消费与当前 question 匹配的判定；跨片段仅保留歌曲级历史供展示，不直接套用旧正确下限。歌曲级平台证据仍可提供弱先验。

v2 的 self_report confidence 也只取当前适用的自报证据；不适用的强自报不能只移除评分却继续给可信度加分。D1 需测试具体范围覆盖一般范围、下调替换、不同版本不继承和重新评估版本变化。

标签自报只建立偏好，不直接宣称具体歌曲熟悉。没抢到、没作答以及输掉对局都不能生成“不认识该歌”的证据。初赛不估计反应速度或获胜概率，也不在本场中途调整题组；反馈结算后用于下一局。

## 5. PRE-04：多人同房间对战

大厅流程：房主创建派对 → n 人加入 → 完成或跳过画像 → 选择多人模式 → 全部参赛者准备 → 生成题组/完成禁歌与评估 → 锁定参赛名单、题目、规则 → 预加载可用音频 → 倒计时 → 抢牌 → 结算排名。

准备分两步：lobbyReady 表示完成入场；题组和禁歌结束后，matchReady 绑定最终评估版本，包含卡牌加载与玩家确认。每次修改最终题组都清空 matchReady，需要再次确认；不能凭修改前的准备状态启动。

为简化初赛，默认同一现场由房主设备/公共音箱播放，其他客户端只显示卡牌并抢牌，避免先做跨设备音频同步。音频就绪检查针对实际播放设备，所有客户端仍须加载卡牌；房主播放失败立即按中断处理。远程各端同步播放另行扩展，不能把共享音箱演示描述为已解决远程同步。

准备状态、在线状态、素材加载状态由服务器维护；只有全部参赛者在线且 ready、素材可用、现有 canStart 通过才能开局。成员/画像/题组/规则变化会清除相关准备与旧确认。开局后新加入者等待下一局，不中途进入计分。

随机只发生在已评估并锁定的题组内部：服务端生成并保存种子，按版本化的 Fisher–Yates 洗牌策略一次生成完整顺序，每题只出一次。同种子/同锁定输入可重放；测试使用固定种子，正式客户端不提前获得种子、未来顺序或答案映射。洗牌不改变题目集合和覆盖结论。

默认多人规则：每题第一名被服务端判定抢对的玩家得到该牌并 +1；该题结束后进入下一题。错抢者本题失去再抢资格，其他人继续；无人抢对则在配置时限结束后跳过。首个可演示版不实现扣分、组合技能或复杂惩罚。客户端只提交 cardId、题目令牌和 actionId，不能提交自报得分或可信的客户端时间。

最终按抢到的牌数降序排名，同分并列（1、1、3）；稳定 ID 只用于显示排列，不偷偷判胜。多人并列无需额外加赛。服务端单线程/串行裁决先受理的有效动作；同一动作去重、关闭题目后的动作拒绝。该规则不声称解决互联网延迟公平，初赛在受控网络验证。

客户端或播放失败时暂停发新题，展示中断状态，由房主结束本局或全员重新准备后新开一局；初赛不做复杂断线续局，也不将断线当作答错。已结束题目的牌数可展示为中断记录，但中断局不提交正式胜负或推动赛事晋级。

## 6. PRE-05：1v1 与现有引擎

1v1 复用现有经典歌牌引擎的布局、播放、抢牌判定和计分规则，不能用多人“第一人 +1”的演示规则覆盖现有引擎。party-runtime 控制准备/公平检查/启动，适配器启动引擎并把事件和最终结果转成统一格式。

在开发前完成 D0 核对：仓库与版本、启动方式、音源/卡牌格式、单场输入、事件协议、服务端真值、结束结果、是否支持多人、同分/暂停能力、许可证。当前仓库没有这些实现，本文不虚构引擎端点或承诺多人已支持。

如果引擎只支持两人，D2 先交付真实 1v1；D3 另实现薄的多人规则适配器，共用题库/画像/房间，不大规模重构引擎。引擎无法输出逐题正误时，只展示比分，不从胜负生成识别证据；补齐事件后才启用对应反馈。

## 7. PRE-06：赛事组织独立于单场引擎

`Party` 是社交房间，`Match` 是一次具体对战，`GameSession` 是该场的引擎运行实例，`Tournament` 是一组 Match 的赛程和晋级关系。单场结果被适配为 MatchResult：matchId、sessionId、参赛者、状态 completed/aborted、胜者或 draw、分数、rulesVersion、resultVersion。不是把所有模式塞入同一套抢牌判定。

赛事组织器拥有 bracket/standings，不拥有单场分数。`recordMatchResult` 校验所属参赛者、场次、完成状态和结果版本，并按 matchId+resultVersion 去重。只有已完成的结果可更新一次晋级；冲突结果进入人工处理，不能覆盖已经开始的下游场次。

**初赛单淘汰默认：** 先支持 4 人/8 人预设，显示八强（8 人时）、半决赛、决赛；每个节点只调用同一个 1v1 接口。对阵使用赛前固定抽签种子，赛中不可重新抽签。其他人数及轮空算法后续增加，不用伪玩家填空。前置比赛未完成不能启动下游；同一玩家不能同时进入两场。组织者是派对房主，身份仍由服务器验证。

同分先使用引擎已有明确决胜规则；引擎只返回平局时进入 awaiting_tiebreak，不自动抽签晋级。组织者发起双方准备的新加赛，取未曝光且可玩的题目并重新评估；缺题或告警仍按规则暂停。弃权需明确记录本人确认或组织者的可审查决定，不能从网络断开直接推断；不伪造识别证据。

**后续小组单循环：** 每组每对玩家只对战一次，胜 3 / 平 1 / 负 0；同分按相互战绩（仅两人同分且交手结果可决胜）再加赛，初赛不实现复杂多队同分排序。跨不同题组的抢牌总数不直接作为全赛事实力排名。小组规模、出线人数、分组再淘汰属于后续配置，不是初赛必须完成的功能。

## 8. PRE-07：比赛题库、画像与公平边界

单场多人按所有本场玩家选曲；1v1 按本场双方选曲；赛事不把未上场观众的画像混进双方评估。赛前固定公共候选题库、选曲/公平配置、规则和用于赛事的画像快照；每场用双方固定快照生成题组，并记录评估。

普通派对下一局使用新反馈画像；正式赛事内的选曲画像保持赛前快照，反馈仍写回个人画像，但只在赛事结束后的新赛事/普通局使用。这样不会因先后出场导致选曲依据不断改变；这是初赛赛事的显式配置，不取消原 Mock 的动态反馈验收。

初赛赛事一台对局顺序运行，共享题目曝光记录，默认排除该赛事已播放的歌曲，包括被旁观者听到的内容。候选不足时暂停，由组织者补充可用内容或明确开启“允许跨场重复”，记录提示并重评；不能静默重复。补库会产生新的 tournamentPoolVersion，已开始比赛保持冻结，未开始比赛的旧题组/确认全部失效。配置和赛事画像快照的修改需结束后新建赛事，不能中途偷偷换规则。

普通局的反馈、题组锁定、赛事快照和新题库版本分别记录。禁止将“选歌阶段的确定性顺序”当成随机播放顺序，也禁止把随机抽题理解为跳过公平选择。

## 9. PRE-08：落到当前仓库的模块

不新增微服务和数据库，延续现有包边界；在需要时增加以下有实际功能的文件：

| 归属 | 新增职责 |
| --- | --- |
| core | recording/question/card、recognition-evidence、room-ready、match/tournament 契约 |
| music-profile | 手动画像转换、score-v2-manual、按题目范围取证据 |
| playlist-engine | 沿用补缺和评估；输入准备层传入可玩歌曲、当前 question 评分及版本 |
| party-runtime | 单场准备/锁定/随机出题计划；`tournament/` 管理对阵、结果去重和晋级 |
| adapters | ManualPreferenceSource、真实 Karuta 适配；必要时增加多人适配；素材清单加载 |
| apps/server | 单进程组合入口、房间会话、REST 意图接口与 WS 状态/动作、内存状态 |
| apps/web | 入房/画像、大厅/准备、选曲告警、对局、排名、赛事对阵页面 |

web 不导入 adapters 或引擎服务器代码；server 持有 runtime，向它注入适配器。初赛不做完整账户体系，server 创建不可猜测的房间成员会话，依据会话判定玩家/房主；请求体中的 playerId/role 不作为身份凭据。API 具体路由和真实引擎接口在 D0/D1 记录后才实现，保留服务端判定与开局检查。

初赛主持保持 MockPartyHostAgent 接口，产品界面显示“系统主持”，输出确定性的开场、选曲理由、告警和结果；不要求 LLM_API_KEY，不安装模型 SDK，不设置大模型生成功能的空页面，也不假装文本来自真实 AI 调用。
